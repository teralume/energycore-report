# Benchmark documental de herramientas DevOps para AV2

**Proyecto:** EnergyCore, equipo Teralume.

**Fecha de revisión documental:** 3 de noviembre de 2026.

**Decisión recomendada:** mantener GitHub Actions para la integración y entrega continua del proyecto.

## Propósito y método

Este documento compara GitHub Actions, GitLab CI/CD y Jenkins según las necesidades de EnergyCore: repositorios en GitHub, trabajo con ramas de GitFlow, backend Java, Web Application Angular, aplicación Flutter y despliegue en Google Cloud Run y Firebase Hosting.

La comparación es **retrospectiva**: GitHub Actions ya forma parte del proyecto y aquí se documentan los fundamentos para conservarlo frente a dos alternativas. No se afirma que este análisis se haya realizado antes de implementar los workflows. La recomendación es una valoración técnica propuesta para el equipo, basada en documentación oficial y en los archivos existentes; no constituye una votación o aprobación de todos los integrantes.

Se revisaron las capacidades documentadas de las tres herramientas y los workflows locales identificados en la sección de evidencia. No se instalaron GitLab ni Jenkins ni se ejecutó el mismo proyecto en tres plataformas. Por ello, este benchmark es una comparación cualitativa de adecuación, no un experimento de rendimiento. No se asignan tiempos, porcentajes de ahorro, tarifas ni puntuaciones que aparenten mediciones.

Los seis criterios son:

1. Integración con repositorios GitHub, ramas, commits y pull requests.
2. Ejecución de pruebas y compilaciones Java, Angular y Flutter, incluyendo disponibilidad de macOS.
3. Conservación de artefactos y composición de etapas de entrega y despliegue.
4. Gestión de secretos, identidad federada y permisos.
5. Trabajo necesario para operar y mantener la infraestructura de CI/CD.
6. Condiciones de acceso y coste que el equipo debe comprobar antes de ampliar su uso.

## Comparación de alternativas

Las capacidades de cada celda proceden de las fuentes enlazadas. Su importancia para EnergyCore y la preferencia final son juicios de adecuación al proyecto.

| Criterio | GitHub Actions | GitLab CI/CD | Jenkins |
|---|---|---|---|
| **1. Repositorios y GitFlow** | Los eventos `push` y `pull_request` activan workflows dentro del mismo repositorio. Permiten asociar verificaciones al cambio que se integra en las ramas del proyecto. No hace falta un espejo adicional. [Eventos de GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). | Puede ejecutar CI/CD manteniendo el código en GitHub mediante integración de repositorios externos y mirroring. La opción documentada requiere Premium o Ultimate y tiene restricciones para pull requests externos, entre ellas los originados en forks. [Repositorios externos](https://docs.gitlab.com/ci/ci_cd_for_external_repos/). | Multibranch Pipeline descubre ramas con un `Jenkinsfile`; la conexión al proveedor y sus credenciales se configuran en Jenkins. Es compatible con una estrategia por ramas, con administración adicional de la integración. [Multibranch](https://www.jenkins.io/doc/book/pipeline/multibranch/), [Pipeline as Code](https://www.jenkins.io/doc/book/pipeline/pipeline-as-code/). |
| **2. Java, Angular, Flutter y macOS** | Ofrece runners administrados Ubuntu, Windows y macOS. Los workflows de EnergyCore ya seleccionan Java, Node y Flutter, y usan `macos-latest` para compilar la aplicación de simulador iOS. La documentación consultada presenta macOS administrado en beta, para planes Premium/Ultimate y programas de código abierto; también permite configurar un runner macOS propio con Xcode. Habría que adaptar y verificar los comandos del proyecto. [Runners administrados](https://docs.gitlab.com/ci/runners/hosted_runners/), [macOS administrado](https://docs.gitlab.com/ci/runners/hosted_runners/macos/), [macOS propio](https://docs.gitlab.com/runner/configuration/macos_setup/). | Los agentes pueden seleccionarse por etiquetas y capacidades. Java, Node, Flutter y Xcode deben estar disponibles en el agente correspondiente; para el objetivo iOS se necesita un agente macOS accesible al equipo. Jenkins permite configurar herramientas por sistema operativo. [Agentes](https://www.jenkins.io/doc/book/using/using-agents/), [Herramientas](https://www.jenkins.io/doc/book/managing/tools/). |
| **3. Artefactos y despliegue** | Permite conservar resultados de pruebas y compilación, compartirlos entre jobs y configurar retención. EnergyCore ya publica JAR, aplicación web, APK, aplicación de simulador y documentos; los jobs de despliegue se condicionan a la verificación previa. [Artefactos](https://docs.github.com/en/actions/tutorials/store-and-share-data) y evidencia E1–E6. | Los jobs pueden guardar artefactos y entregarlos a etapas posteriores. Los environments identifican destinos de despliegue. La documentación distingue artefactos temporales de registros de paquetes para entregas versionadas duraderas. [Artefactos](https://docs.gitlab.com/ci/jobs/job_artifacts/), [Environments](https://docs.gitlab.com/ci/environments/). | Un `Jenkinsfile` puede definir etapas de build, test y deploy; `archiveArtifacts` conserva archivos del build. El equipo tendría que preparar el pipeline, el almacenamiento y la conexión con los servicios de destino. [Jenkinsfile](https://www.jenkins.io/doc/book/pipeline/jenkinsfile/), [archiveArtifacts](https://www.jenkins.io/doc/pipeline/steps/core/#archiveartifacts-archive-the-artifacts). |
| **4. Secretos, OIDC y permisos** | `GITHUB_TOKEN` admite permisos mínimos por workflow/job. OIDC requiere `id-token: write` y una relación de confianza configurada en el proveedor. En EnergyCore, el deploy de backend declara OIDC; los deploys Firebase referencian un secreto de cuenta de servicio. La declaración YAML no demuestra que dichas credenciales estén configuradas o que el despliegue haya ocurrido. [Permisos del token](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token), [OIDC](https://docs.github.com/en/actions/reference/security/oidc). | Admite variables de CI/CD protegidas o enmascaradas y tokens de identidad OIDC con audiencia configurable. Su uso exige configurar las restricciones del job y la confianza en el servicio externo. [Variables](https://docs.gitlab.com/ci/variables/), [ID tokens](https://docs.gitlab.com/ci/secrets/id_token_authentication/). | Las credenciales se referencian por identificador y ámbito. El plugin OpenID Connect Provider puede emitir tokens para autenticación de builds ante servicios externos; requiere configurar emisor, audiencia y confianza. No debe confundirse con el plugin de inicio de sesión OIDC de usuarios. [Credenciales](https://www.jenkins.io/doc/book/using/using-credentials/), [OIDC Provider](https://plugins.jenkins.io/oidc-provider/). |
| **5. Operación y mantenimiento** | GitHub mantiene las máquinas e imágenes de sus runners administrados. El equipo conserva la responsabilidad de los workflows, dependencias, permisos y compatibilidad con actualizaciones. Es la opción que aprovecha directamente la configuración existente de EnergyCore. [Runners administrados](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners). | Con runners administrados, GitLab gestiona la infraestructura de ejecución; con runners propios, el equipo debe operarlos. Para este proyecto se añade la integración con GitHub y la adaptación de los pipelines. [Runners administrados](https://docs.gitlab.com/ci/runners/hosted_runners/), [Repositorios externos](https://docs.gitlab.com/ci/ci_cd_for_external_repos/). | La instalación requiere mantener controlador, agentes, herramientas, plugins y configuración de seguridad. Aporta control sobre el entorno, pero introduce responsabilidades que EnergyCore no necesita asumir para conservar su CI actual. Esta valoración de esfuerzo es cualitativa. [Administración de Jenkins](https://www.jenkins.io/doc/book/managing/). |
| **6. Acceso y coste como condición** | El uso de runners estándar en repositorios públicos tiene condiciones de gratuidad documentadas; repositorios privados, runners mayores y almacenamiento tienen reglas distintas. Deben revisarse el plan, los presupuestos y la retención de artefactos de la cuenta real. No se declara coste total cero. [Facturación de Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions). | Deben comprobarse elegibilidad de integración externa/macOS, plan y cuotas de cómputo. Los factores de consumo dependen del runner y no equivalen por sí mismos a una tarifa monetaria. No se presupone una licencia o beneficio académico disponible para el equipo. [Cómputo](https://docs.gitlab.com/ci/pipelines/compute_minutes/), [macOS](https://docs.gitlab.com/ci/runners/hosted_runners/macos/). | Jenkins se distribuye bajo licencia MIT. Esto no elimina el coste de infraestructura, almacenamiento, un agente Mac o el tiempo de administración. No se cotizaron servicios ni horas de operación. [Licencia](https://www.jenkins.io/license/), [Administración](https://www.jenkins.io/doc/book/managing/). |

GitFlow es una convención de colaboración y ramas que puede implementarse con cualquiera de las alternativas. Usar una herramienta de CI/CD no configura por sí solo protección de ramas, revisión humana o promoción segura a producción.

Esto respalda la adecuación de Actions al proyecto, sin convertir la lectura de YAML en una afirmación de que todas las ejecuciones actuales están aprobadas.

## Decisión y justificación

**Se recomienda conservar GitHub Actions.** La selección retrospectiva se sustenta en cuatro razones concretas:

1. Los cinco repositorios ya contienen workflows revisables junto con su código y sus ramas. La solución permite continuar la trazabilidad existente de commits, verificaciones y artefactos.
2. El stack Java/Angular/Flutter está expresado en jobs reales. La necesidad de compilar para el simulador iOS ya está contemplada mediante un runner macOS administrado, aunque eso no equivale a validar la aplicación en un iPhone.
3. El equipo puede conservar la infraestructura administrada y concentrarse en la calidad de los tests y de los controles de despliegue. Para el alcance actual, no se identifica un requisito que justifique añadir un controlador Jenkins o una integración adicional GitLab–GitHub.
4. Existe un mecanismo concreto de permisos mínimos y una vía OIDC declarada para Cloud Run. El trabajo restante consiste en verificar y completar los controles del proyecto, no en sustituir la herramienta por falta de capacidad básica.

GitLab CI/CD sigue siendo una alternativa viable si el equipo decide concentrar repositorios, planificación y CI/CD en GitLab o dispone de la elegibilidad necesaria para su integración externa y macOS. Jenkins sería razonable si surgiera una necesidad de agentes propios, acceso a hardware o control del entorno que justificara su operación. Ninguna alternativa se descarta por carecer de pruebas, artefactos u OIDC.

## Límites de CD y monitoreo que conserva AV2

**Entrega frente a despliegue.** Publicar un artefacto validado demuestra preparación de una entrega. El deploy automatizado de E1–E3 depende de variables, credenciales, permisos del proveedor y de que el job se ejecute correctamente. No se consultaron valores de secretos. La inspección operativa complementaria del 03/11/2026 sí verificó la condición de facturación del proyecto, sin modificarla; su evidencia se enlaza en el alcance del monitor. Un job `skipped` no es un despliegue aprobado.

**Promoción del artefacto.** E1 despliega desde `source: .` y E2 reconstruye la Web Application dentro del job de despliegue. Los archivos inspeccionados no demuestran promoción del mismo binario inmutable publicado por el job de verificación. Tampoco declaran un entorno de staging ni una reversión automática. Estas condiciones deben describirse como límites de la implementación, no como funcionalidades realizadas por disponer de GitHub Actions.

**Comprobación posterior al despliegue.** La línea base E1 consultaba `/actuator/health`, mientras E6 comprueba `/api/v1/health`. El [commit de corrección `3bfc0b5`](https://github.com/teralume/energycore-platform/commit/3bfc0b52ebdb791b946d1186118bdbaea26b12a0) cambia el smoke a `/api/v1/health` y exige un objeto JSON con `status=UP`; también conserva los reportes de pruebas ante fallo. La nueva ejecución detectó además una prueba que solicitaba un período fijo de octubre para una lectura registrada con la fecha actual. El [commit `abd1964`](https://github.com/teralume/energycore-platform/commit/abd196438d3d1bd8f7de951aab31fae4aa0e0753) obtiene la fecha de esa lectura y conserva las aserciones de creación y eliminación. La integración en [main `3f74d478`, run `41646065500`](https://github.com/teralume/energycore-platform/actions/runs/41646065500) aprobó 28 pruebas JUnit y 60 escenarios Cucumber, 88 en total, sin fallos, errores ni omisiones, y publicó reportes y JAR. CI terminó en `success`; CD terminó en `skipped`. La corrección del YAML y las pruebas no acreditan un despliegue ejecutado; la recuperación pública se demuestra por separado con el monitor.

**Alcance del monitor.** E6 verifica respuestas puntuales de tres superficies públicas: health con `status: UP`, un contrato OpenAPI 3 con rutas y una página HTML. El [registro de activación del 21/10/2026](../assets/evidence/implemented/av2-monitoring-activation-2026-10-21.json) conserva una [ejecución remota aprobada](https://github.com/teralume/energycore-report/actions/runs/39565142305) de esa fecha. La [comprobación del 03/11/2026 a las 13:08:52 UTC (08:08:52 de Lima)](../assets/evidence/implemented/av2-monitoring-2026-11-03.json) registra health/OpenAPI 503 y web 200. El proveedor atribuyó el rechazo a facturación deshabilitada y cuenta cerrada en ese momento; ese registro se conserva como incidente histórico. Después de la reactivación comunicada en la sesión, la [ejecución `41651099079`](https://github.com/teralume/energycore-report/actions/runs/41651099079), sobre `e1e26416`, obtuvo las tres respuestas válidas con HTTP 200 el 03/11 a las 14:10:53 UTC (09:10:53 de Lima). El [registro de recuperación](../assets/evidence/implemented/av2-recovery-2026-11-03.json) conserva jobs, artefacto y resultados. Esto acredita recuperación puntual, no disponibilidad continua, SLA, percentiles, navegación autenticada completa ni medición de energía física. No se deduce de las dos sondas el inicio o la duración exacta del incidente.

**Cobertura verificable del pipeline.** La [matriz de capacidades y evidencias](github-actions-av2.md#matriz-de-capacidades-y-evidencia-del-pipeline) relaciona integración, tests, build, artefactos, despliegue condicional, smoke y operación con sus jobs y resultados. Distingue lo ejecutado de staging, aprobación protegida, promoción binaria y avisos no acreditados. No se calcula un porcentaje a partir de un conteo arbitrario de etapas ni se declara cumplido el umbral de 50 % de la rúbrica sin un alcance y ponderación acordados.

**Periodicidad.** El cron declara una comprobación cada seis horas. GitHub advierte que los eventos programados pueden retrasarse y que, en repositorios públicos, pueden deshabilitarse tras 60 días sin actividad. Por eso el workflow no se presenta como un monitor de disponibilidad en tiempo real ni con horario garantizado. [Condiciones del evento schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

**Alcance académico.** Esta comparación fundamenta la herramienta DevOps empleada en AV2. No agrega ejecución experimental, resultados de tratamiento, shareback ni pre-launch de TB2. Las entrevistas, revisiones humanas y auditorías externas conservan su propia evidencia y no se sustituyen por este benchmark.

## Criterio para revisar la decisión

La recomendación debe revisarse si cambian el alojamiento de los repositorios, las condiciones de macOS o de cómputo, los requisitos de seguridad, la necesidad de hardware propio o el esfuerzo observado para mantener los pipelines. Antes de afirmar que una alternativa es más rápida o económica, se requiere ejecutar cargas equivalentes, fijar versiones y recursos, registrar varias corridas y separar tiempo de cola, ejecución, almacenamiento y operación. Ese experimento comparativo no se realizó en este documento.
